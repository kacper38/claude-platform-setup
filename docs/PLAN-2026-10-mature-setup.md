## 1. Assumptions

1. **System of record = GitHub for now** (Issues, PRs, Actions) for your own repos. The tracker's `Backend` protocol is the seam through which Forgejo (Appendix A) or a work tracker (GitHub Enterprise as is; Jira/ADO behind a later adapter) slots in. GitHub cannot enforce one-label-per-scope server-side: the CLI enforces it on every write and a `label-lint` Action reports violations without ever changing a label; the gap is recorded.
2. **The kit is files in the repo**, not a Claude plugin and not user scope: `AGENTS.md` (canonical working agreement; `CLAUDE.md` is the one line `@AGENTS.md`), `.claude/settings.json` (hooks → `guard`; read by Claude Code and by VS Code Copilot), `.github/hooks/guard.json` (the same hooks for Copilot CLI and the cloud agent), `.claude/skills/` and `.claude/agents/` (both read by Claude Code and by VS Code), `tools/guard/` and `tools/tracker/` (stdlib Python, vendored, version-stamped), `.githooks/commit-msg`, `.github/workflows/`, `.github/ISSUE_TEMPLATE/`, `.claude/guard.json` (per-repo knobs). Source of truth is `kit/` in this repo plus the root `agents/` and `skills/`; `install.sh --into <repo>` copies idempotently and writes the source commit to `.claude/kit-version`. This repo installs the kit into itself. The Claude plugin/marketplace packaging is deferred (Appendix A); at work the distribution channel is the org's `.github-private`, not a marketplace.
3. **`guard` is harness-neutral**: it reads the hook JSON on stdin, normalizes event and tool class across both input shapes (Claude: `Bash`/`Read`/`Write`/`Edit`/`Agent`; Copilot: `bash`/`powershell`/`view`/`create`/`edit`/`task`), applies deterministic rules, answers with `permissionDecision` + `permissionDecisionReason` (top level and under `hookSpecificOutput`; each harness reads one of them) and exit 2 on deny. Budget 2 s, no network in PreToolUse: Copilot hook timeouts fail OPEN for every event, and the cloud agent turns `ask` into `deny`. Fixtures: allow/ask/deny/crash × {claude, copilot} per rule, captured from real sessions (step 1.3), redacted, run in CI.
4. Verified against the VS Code and GitHub docs on 2026-10-29: Copilot reads hooks from `.github/hooks/*.json` and from the `hooks` field of `.claude/settings.json` (VS Code; the cloud agent only from `.github/hooks`); events PreToolUse/PostToolUse/SessionStart/UserPromptSubmit/Stop/PreCompact in VS Code, plus SessionEnd and SubagentStart/Stop in the CLI; Agent Skills from `.github/skills/`, `.claude/skills/`, `.agents/skills/` and the `~/.copilot|.claude|.agents/skills` homes; instructions from `AGENTS.md`, `CLAUDE.md` or `.github/copilot-instructions.md`; custom agents from `.github/agents/*.agent.md` and from `.claude/agents/*.md` in Claude format; org/enterprise agents and `copilot/managed-settings.json` live in `.github-private`. Kacper confirmed hooks, skills and MCP policies are enabled at work.
5. Unverified, each a one-commit probe before anything depends on it, results to DECISIONS.md: Copilot `tool_input` shape per tool (captured in step 1.3); whether VS Code honours Claude `tools:` names in `.claude/agents` or needs its own identifiers; whether the `matcher` structure in `.claude/settings.json` filters in VS Code (guard self-filters, so a miss costs latency only); whether `chat.useAgentsMdFile` is on at work (fallback: `.github/copilot-instructions.md` = "Read AGENTS.md first"); the `model:` strings the work picker accepts; and the rev 4 Claude list (Agent tool name in PreToolUse, Workflow pass-through, transcript format, auto-memory write path, `claude -p` flags, `isatty` from Bash, hook snapshotting).
6. Every hook is deterministic stdlib Python with an allow/ask/deny fixture corpus plus a crash fixture, run in CI. Fleet's Bash verifier stays the only model-backed hook. No LLM judge in PreToolUse (your trap: a judge blocked valid `git -D` / worktree commands).
7. Nothing deletes: memories are deprecated, index content is under git before anything regenerates it, worktrees move by hand, the tracker has no delete/force/close-without-protocol verb.
8. Vendor boundary: Anthropic for code and reviews at home; Gemini for plans/designs in non-client repos; the local llama-server only while a fleet batch already has it up; at work only what the org's Copilot offers.
9. The account is subscription-billed: the ledger reports tokens plus API-equivalent USD (Claude Code only).
10. Pilots: this repo dogfoods the kit and the tracker (the plan's own steps become its first issues); kacper-agent and agent-fleet follow; ArtEventOS moves its `/next-task` loop onto the GitHub adapter; **one work repo** gets the kit in step 3.9 with `KZ_BOUNDARY=client`. Nothing from home (memory, telemetry, tokens, transcripts) crosses to work, and the kit itself carries no client data: it is public MIT files only.
11. Hosting is dormant: nothing in phases 1–3 waits for pierun, a VPS or Forgejo. When Appendix A lands, only the tracker backend, the OIDC issuer and the memory/backup targets change.

## 7. What an auditor gains (and does not)

Gains one queryable, server-timestamped chain per change on GitHub: scope approved by a named human (ready), execution start (claim), independent evidence (checks on the merge SHA, review receipt or Copilot review, decision issues), human closure with cross-references; the rule "who may perform which transition" exists as tested code, as a hook that fires in both harnesses, and (with the bot identity) as separate principals; the active policy version is a commit hash in the repo. Does not gain: server-enforced label exclusivity (client-side + lint until Forgejo), proof the human review was substantive, proof the requirements were right, or retention under your own control (GitHub's, until Appendix A).
