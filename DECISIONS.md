- Here-document bodies are data, not commands: `secret-shell`, `git-guard`, `deploy-ask` and `egress-guard` strip them before judging (the delete-guard keeps scanning them, per the owner rule) — found by dogfood: the guard went live in the session that wrote it and denied a commit whose message quoted `echo X=1 > .env`; revisit if: a heredoc is used to smuggle a write past the guard (then the body is scanned for redirect targets only).

## 2026-10-29 — steps 2.2 + 2.3: protected-branch and fan-out rules

- `protected-branch` is path-scoped: the checkout that owns the *file* decides (walk up to its `.git`, then `git symbolic-ref`), not the session's cwd, so editing `~/Documents/TechVault/x.md` from a repo on `main` passes and editing a file of a repo on `main` from anywhere is denied. `git commit` is denied when the repo it runs in (cwd or `git -C <dir>`) is on a protected branch; `merge`/`cherry-pick`/`rebase` are not covered on purpose (`git merge --ff-only` is how `main` is synced; the push guard catches the rest). Files under `.git/` are never judged. The protected set is `protected_branches` in `.claude/guard.json` (default `main`, same set as git-guard and the GitHub ruleset of step 2.8). ArtEventOS keeps its inline hook until step 3.8 (its settings run live in Kacper's other sessions; swapping is done together with the tracker adapter there). Revisit if: a repo needs per-path exemptions (then a `protected_allow` list, not a looser default).
- `fan-out` never denies: it appends `{ts, event, harness, session, agent, model, agent_id, cwd}` to `<telemetry_dir>/spawns.jsonl` on every spawn (`PreToolUse` on `Agent`/`Task`/`task`, and `SubagentStart` in Claude Code) and returns `ask` at the 6th `PreToolUse` spawn of a session and every 10th after (6, 16, 26, …), with a note when `127.0.0.1:8012` answers (llama-server, 39 GB). Counting uses the harness `session_id`, so a long session is one budget; the log is scanned on each spawn (fine below ~10⁴ lines; rotate monthly if it grows). The Copilot `.github/hooks/guard.json` gets no `SubagentStart` entry: VS Code does not list that event, so the `task` tool's `PreToolUse` is the only Copilot signal (counts spawns, logs no model). Cost angle: the prompt is the hook-level version of the "<=5 agents, brief first" guardrail in `~/.claude/CLAUDE.md`; it costs nothing when nobody fans out. Revisit if: a legitimate workflow needs >5 agents routinely (then raise `FANOUT_FIRST` in `.claude/guard.json`, which is not a knob yet on purpose).

## 2026-10-29 — step 2.1: guard-the-guard

- `guard-config` returns `ask` on every Edit/Write of hook configuration: `.claude/settings*.json`, `.claude/guard.json`, `.github/hooks/**`, `tools/guard/**` in any repo, and `~/.claude/settings*.json`, `~/.claude/hooks/**` for Claude Code. Revisit if: the prompt becomes noise in this repo, which develops the guard (then narrow `tools/guard/**` to `guard.py`, never drop the config paths).

## 2026-10-29 — step 2.4: tracker data model on GitHub Issues

- Label families `type/*` (5) and `status/*` (7) and the transition table live as data in `tools/tracker/tracker.py`; every triple outside the table raises (`tools/tracker/tests/test_model.py`). Exclusivity is the CLI's job (add the new status, then remove the siblings) and `label-lint` only reports: one comment per issue and finding set (a fingerprint in a hidden marker keeps it idempotent), one tracking issue kept current, labels never touched, exit 0 so a label mistake never turns an issue-event run red. Events extended beyond the plan (`closed`, `reopened` added) so "closed without done" is caught at once, not nightly. Issue forms `task.yml` and `bug.yml` carry the definition-of-ready fields and blank issues are off. The "body frozen after ready" record is a sha of the body with line endings and the state of acceptance boxes normalised away, recorded by `owner ready` and re-checked by `owner done`, so the owner can tick boxes without breaking the freeze. Cost: GitHub Issues are free; the nightly `label-lint` run is about a minute of Actions time per day, inside the free tier (€0/month). Compliance angle: the issue is the change record, the transition table is the approval matrix, and every move leaves a comment with who, when and on which branch. Revisit if: a repo needs more status values (then a per-repo extension of the table, not a free-text status).

## 2026-10-29 — step 3.1: commit-msg gate

- One stdlib script, three entry points: the `commit-msg` hook (`.githooks/commit-msg`, activated by `core.hooksPath` which the installer sets in git targets and this clone sets by hand), the CI job `commit-msg` on the PR range, and `--message` for tests. Rules: `type(scope): subject` with eleven types, subject ≤72, lower-case start, no trailing period, a blocklist of past/gerund first words as the "imperative" check (a grammar check is not worth a dependency), no closing keyword anywhere (`Fixes #N` closes behind the tracker; `Refs #N` is the form), trailers only in the last block. Merge/Revert/fixup!/squash! pass. `--no-verify` is already denied by git-guard, which is the "commit-gate" the plan named. `core.hooksPath` hides any hooks in `.git/hooks` of that clone; recorded here because it surprises. Cost: €0. Compliance angle: the commit message is the first line of the change record; the gate makes its shape a tested rule, and CI re-checking means a hook skipped on a laptop still fails the PR. Revisit if: a repo needs a ticket key in the subject (then a per-repo regex, not a global one).

## 2026-10-29 — step 3.2: egress screen

## 2026-10-29 — step 3.4: memory under git

- `tools/memory/memstore.py`: one bare repository `~/.claude/memory-store.git` whose work tree is `~/.claude/projects`, with `info/exclude` letting only `*/memory/**` in (transcripts, tool results and scratch never enter it). Chosen over per-project repos (the memory dir is not a repo and Claude Code owns the directory layout) and over copying files elsewhere (a copy drifts). Every memory write through Write/Edit becomes one commit via the PostToolUse hook (`memstore.py hook`), message `memory(<slug>): add|update|delete <name>`; a deletion made with a shell command is picked up by the next commit for that project (the hook stages the whole `<slug>/memory` directory, so such a commit may carry `+N more`). Push is off: `push` needs a remote `origin` and `KZ_MEMORY_PUSH=<slug,...>|*`, and refuses when unpushed commits touch a project outside the allowlist (the first push counts every commit). Cost: $0 (private GitHub repo, local git). Compliance angle: memory is a record the agent writes about the work; git gives it history, authorship and diffs, and the allowlist keeps client-project memory off GitHub (the work machine never runs this at all, see `docs/USING-AT-WORK.md`). Revisit if: memory moves into a Claude Code built-in sync (then the hook becomes a no-op) or a project needs memory shared across machines (then a per-slug remote).
- Wiring: this repo's `.claude/settings.json` runs the hook and a SessionStart digest (`memstore.py digest`, ≤ 8 lines, ≤ 600 bytes) for its own sessions; the user-scope lines for `~/.claude/settings.json` are the owner's to add (guard-the-guard rule, step 2.1). Remote creation (`kacper38/memory-store`, private) is the owner's too.

## 2026-10-29 — step 3.5: memory schema, validator, index

- Schema = the existing frontmatter plus optional `metadata.status` (`active` default | `deprecated` | `superseded` + `superseded_by`), `stale_after: YYYY-MM-DD` (required for `project` and `reference`, the two types that age), `verified: true` + `verified_on`. No `trap` field: a memory that would mislead gets `status: deprecated` with the reason in its body, which costs no new vocabulary. The validator (`memstore.py validate`, also run by the hook with exit 2 = feedback to the agent) warns and never blocks: the file is committed first, so a half-written memory is a visible commit, not a lost one. Lenient on purpose: ~90 existing files lack `stale_after`; `triage` lists them and the index and digest keep working. Compliance angle: `stale_after` plus `verified_on` make "when was this last true" answerable, which the plan's ALCOA+ line asks of every record the agent relies on. Revisit if: warnings get ignored for a month (then `stale_after` becomes a deny for new files of those types).
- `memstore.py index --write` regenerates `MEMORY.md` from frontmatter (active files only, sorted by type then name, ≤ 18 KB with an explicit "N more not indexed" line) instead of the hand-kept list; the cap exists because Claude Code loads the index whole and truncates it silently past ~25 KB. `deprecate <file> [--by slug]` edits the `metadata:` block in place and commits. Revisit if: the index needs grouping by type (then headings, same cap).
